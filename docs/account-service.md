# Account service

Accounts extend the existing metadata application as an optional, independent module. Legacy v1 room credentials are unchanged and are not authenticated Google room membership. See [accounts and rooms](architecture/accounts-and-rooms.md).

Configure the confidential backend with `SYNCWATCH_GOOGLE_CLIENT_FILE` (protected Google Web-client JSON), `SYNCWATCH_PUBLIC_ORIGIN` (exact HTTPS origin), and `SYNCWATCH_ACCOUNT_DIRECTORY` (private persistent directory). All three are required together. The registered callback must equal `<origin>/auth/google/callback`. Literal `http://127.0.0.1` is permitted only for local development. Requests must match the configured origin; untrusted forwarded headers, browser CORS, redirects to another API origin and arbitrary OAuth endpoints are unsupported. Account-enabled storage currently requires Windows DPAPI. Keep the configuration, protected account snapshot and key ring outside source/build/package directories with owner-only access. Back up and restore the protected key ring and snapshot together; key loss must fail closed.

The native API returns JSON `{ "v": 2, "result": ... }`; typed errors return `{ "v": 2, "error": { "code": ... } }`. Native request bodies are JSON objects with `v: 2`, no unknown or duplicate fields, and at most 4096 bytes. The endpoints accept no browser Origin header. Responses never return Google tokens. Clients bound response bytes and reject redirects.

| Request | Body or header | Result |
| --- | --- | --- |
| `POST /v2/account/sign-ins` | `challenge`: base64url SHA-256 of an in-memory 256-bit verifier | `transactionId`, same-origin `browserUri`, `expiresIn: 300`, `pollAfterMs: 2000` |
| `POST /v2/account/sign-ins/{id}/poll` | `proof`: verifier | `status`; proposed `account` only for `confirmAccount`; no device credential |
| `POST /v2/account/sign-ins/{id}/verify` | `proof`, `browserProof` shown only by the browser | Proposed account, after browser counterproof verification |
| `POST /v2/account/sign-ins/{id}/confirm` | `proof`, `browserProof`, random `requestId` | `status: complete`, `session` after native account confirmation |
| `POST /v2/account/sign-ins/{id}/cancel` | `proof` | `status: cancelled`; revokes a completed transaction's device session while its receipt remains available |
| `GET /v2/account/me` | `Authorization: Bearer <accessToken>` | Current account profile |
| `POST /v2/account/refresh` | `refreshToken`, random `requestId` | Rotated `session` |
| `POST /v2/account/logout` | No body; `Authorization: Bearer <refreshToken>` | `status: signedOut` |

Each JSON request body includes `v: 2`. A profile has opaque `id`, `name` and verified `email`; a pre-confirmation proposal has an empty ID. A session contains `account`, opaque `accessToken`, opaque `refreshToken`, and `expiresIn: 600`. Opaque credentials, proof, transaction and request identifiers use 32 random bytes encoded as 43 unpadded base64url characters. They are not diagnostic strings, URLs or clipboard data. The separate browser code is a short-lived, proof-bound counterproof, not a SyncWatch access/refresh credential or a Google verification code; enter it only in the initiating SyncWatch window.

Transaction states are `pending`, `authorizing`, `browserConfirmationRequired`, `confirmAccount`, `complete`, `cancelled`, and `failed`. Only its proof-owning native client can inspect or confirm a transaction. Opening its browser URL is not authentication. An identical confirmation retry returns its original result for 30 seconds; a different confirmation cannot consume it again. The browser alone displays a separate 12-character uppercase hexadecimal confirmation code. It is not returned by polling; the proposed profile is withheld until that code and the native verifier are checked together. Three wrong code attempts close the transaction. The native client then shows the verified account for a separate confirmation before a session is issued. A forwarded sign-in URL and its originating verifier alone cannot disclose the profile or issue a device credential. Browser pages contain no session tokens, profile, scripts or native application bridge. The OAuth handler consumes the browser correlation cookie and protected state; it uses PKCE and fixed Google endpoints. The backend reads verified profile data over its authenticated UserInfo backchannel and never decodes an ID token.

Access credentials expire after ten minutes; refresh families have a thirty-day absolute limit. A refresh rotates both credentials and invalidates the old access token. An identical refresh request may recover its original result for thirty seconds. Any retired refresh-token reuse outside that exact latest retry revokes its device family. History is bounded to 4096 rotations, after which a new sign-in is required. Background cleanup removes expired transactions, sessions and encrypted retry responses. Request/global transaction/store bounds fail closed.

Desktop controllers restore a saved SyncWatch session from macOS Keychain, current-user Windows Credential Manager or Linux Secret Service. Closing the application preserves a remembered session. Sign out revokes the device session and removes its local record; remote or local failure stays visible. It does not sign Google out or end an external Meet call. Startup never opens a room, browser or call automatically.

The private, versioned record contains only the service origin, account binding, refresh credential and the next rotation request identifier. Access credentials and profile display data stay in memory. The controller saves the next checkpoint before presenting a restored or newly confirmed session as signed in. A profile has an exclusive process lease, including protection against multiple same-process owners on Linux. No credential is written to the lease or preferences. Record decoding rejects unknown/duplicate fields, invalid origins, unexpected versions and oversized input.

Unavailable or locked storage, rejected records and failed restoration expose Retry, Forget on this device and Use memory only through common Design. Memory-only continuation is explicit and leaves an older saved record unchanged. A rejected/revoked session clears its local record and requests a fresh sign-in. Exact rotation retries reuse the persisted request identifier within the server's thirty-second recovery window; a crash or interruption beyond that window can require a new sign-in. No plaintext fallback or indefinite replay of retired credentials is supported.

`AccountCredentialVault` and `AccountSessionStore` remain separate from the HTTP client. Their native integration checks use disposable scopes and synthetic bytes; opt in with `SYNCWATCH_ACCOUNT_VAULT_CHECKS=1` for macOS/Windows or an owned helper path in `SYNCWATCH_ACCOUNT_VAULT_HELPER` on Linux. Linux can qualify against an isolated native Secret Service without changing the user's desktop keyring. These library checks do not substitute for application-window sign-in, restart, recovery and sign-out acceptance. All-device logout, authenticated room/Syncplay admission, organizer consent, automatic Meet provisioning and complete call acceptance remain incomplete.
